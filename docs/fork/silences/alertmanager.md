# Сайленсы Keep ↔ Alertmanager

## Владение и права

- Сайленс, созданный в Keep, управляется через обычные команды Keep с проверкой
  роли, команды и ревизии. Служебные ID Alertmanager сохраняются в
  `silence.external_context`; это поле нельзя передать в API-команде.
  `correlation_id` остаётся метаданными и никогда не разрешает внешний DELETE.
- Правило, созданное непосредственно в Alertmanager, импортируется отдельно
  для каждой команды Keep. Оно подавляет подходящие уведомления внутри этой
  команды. API/UI показывают `read_only=true`; изменение и отмена выполняются
  в Alertmanager. Локальная команда возвращает `409 externally_managed_silence`.
- Создание, изменение и отмена импортированного правила, а также внешняя отмена
  правила Keep записывают `SilenceEvent` и настроенные доставки в одной
  транзакции. Подписчики и транспорт задаются существующим IaC bundle.
  `mm-bridge` для этой доработки не меняется.

## Конфигурация IaC

Переменные backend:

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `KEEP_ALERTMANAGER_URL` | отсутствует | Базовый URL Alertmanager; также поддерживается `ALERTMANAGER_URL` |
| `KEEP_ALERTMANAGER_RECONCILER_ENABLED` | авто по URL | `true/1/yes` включает; `false/0/no` явно выключает даже при заданном URL |
| `KEEP_ALERTMANAGER_TEAM_MATCHERS` | `{}` | JSON: ID команды → список альтернативных наборов положительных точных matchers |
| `KEEP_ALERTMANAGER_GRACE_PERIOD_SECONDS` | `180` | Защита свежих алертов от автозакрытия |
| `KEEP_ALERTMANAGER_CONSECUTIVE_MISSES` | `2` | Сколько последовательных успешных снимков должны подтвердить отсутствие алерта |
| `KEEP_ALERTMANAGER_DROP_RATIO_CIRCUIT_BREAKER` | `0.5` | Порог резкого падения количества алертов |
| `KEEP_ALERTMANAGER_CIRCUIT_GRACE_SECONDS` | `180` | Сколько секунд должен оставаться стабильным уменьшенный или пустой снимок перед восстановлением |
| `KEEP_ALERTMANAGER_RECONCILE_INTERVAL_SECONDS` | `60` | Общий минимальный интервал опроса между воркерами |
| `KEEP_ALERTMANAGER_LEASE_SECONDS` | `120` | Срок аренды общей блокировки; должен быть больше `20` секунд |

Пример значения `KEEP_ALERTMANAGER_TEAM_MATCHERS`:

```json
{
  "engineering": [[{"name": "owner", "value": "engineering"}]],
  "platform": [[{"name": "owner", "value": "platform"}]]
}
```

Внутри набора действует AND, между наборами одной команды — OR. Имена команд и
labels произвольные. Границы разных команд должны исключать одновременное
совпадение; перекрывающаяся конфигурация отклоняется. `__unassigned__` обозначает
объекты без команды; этот scope также требует явной границы по labels.

Границы относятся к **исходным labels Alertmanager**. Они должны соответствовать
правилам назначения команды в Keep. Из canonical `team_id` нельзя автоматически
вывести raw matcher: команда может назначаться mapping rule по другим полям.
Без настроенной границы правило продолжает действовать в Keep, но наружу не
экспортируется; API/UI показывают причину `team_scope_unconfigured`.

## Селекторы и синхронизация

- Для алерта экспортируется весь набор его исходных непустых labels, включая
  `alertname`, instance, cluster и namespace, если они есть. Для нескольких
  fingerprints/членов инцидента создаются отдельные внешние правила. Наборы
  labels разных целей не объединяются в более широкий фильтр.
- История fingerprint с чужой командой, несовпадающая граница команды и
  отсутствующие исходные labels блокируют экспорт.
- CEL экспортируется только как конъюнкция положительных сравнений
  `labels["field"] == "nonempty value"` или `labels.field == "nonempty value"`.
  Отрицания, OR, regex и условия по другим полям остаются локальными правилами
  с `local_only / unsupported_filter`. Сайленс без срока окончания также остаётся
  в Keep: `indefinite_silence`.
- При импорте используются RE2 и полное совпадение строки, включая Unicode
  classes и inline flags. Отсутствующая label считается пустой строкой, как
  в Alertmanager. Пустой/невалидный набор matchers отклоняется.
- Изменение срока и комментария в Keep отправляется на существующий внешний
  ID. Учитывается изменение времени начала сервером Alertmanager. Изменение
  селектора сначала отменяет старое внешнее покрытие. Если отмена не подтверждена,
  новое покрытие не добавляется; виден `uncertain / cancellation_unavailable`.
- Аренда в `alertmanagerreconciliationstate` защищает опрос/POST от параллельных
  gunicorn workers. Аренда проверяется перед внешними действиями и записью
  результата; устаревший воркер не может подтвердить чужую аренду.
- Перед POST сохраняется intent с приватным nonce в комментарии. После потери
  ответа успешное создание подтверждается следующей инвентаризацией. Пока исход
  запроса неизвестен, второй слепой POST не выполняется; виден `uncertain`.
  При недоступности источника счётчики пропусков сбрасываются.

Времена в подтверждении intent сравниваются с точностью JSON API Alertmanager:
`strfmt.DateTime` возвращает миллисекунды. Сроки в Keep сохраняют микросекунды.
Это позволяет подтвердить принятый POST после потери ответа; изменение внешнего
срока на одну миллисекунду уже не считается тем же intent.

Публичный `synchronization` содержит только source digest, состояние и причину;
внешние ID и nonce наружу через Keep API не возвращаются.

## Обновление существующей установки

1. Применить обычным процессом раскатки Alembic migration `e73b914a620c`
   после `d39b72e4a610`. Миграция добавляет JSON receipts и таблицу аренды,
   сохраняет существующие правила/журнал. Downgrade отказывается терять
   сохранённые receipts или состояние reconciliation.
2. Настроить явные границы команд и пересобрать backend. На Alpine нужны
   runtime `re2` и build dependencies `re2-dev`, `py3-pybind11-dev`; они добавлены
   в Dockerfile. Python dependency и lock содержат `google-re2==1.1.20251105`.
3. Проверить старые записи `correlation_id=am_synced:...` и соответствующие
   внешние правила **вручную с правами администратора Alertmanager**. Эти ID
   ранее могли задаваться пользователем, поэтому автоматически принять их как
   разрешение на DELETE нельзя. Keep показывает
   `local_only / legacy_binding_requires_review`; новые экспорты таких правил
   не создаются. Старые широкие внешние правила требуют отдельной сверки и
   завершения в источнике, затем нужное правило создаётся через новый контракт.

Старые импортированные акторы `system/name` отображаются как `service` уже до
первого опроса; опрос обновляет сохранённое представление. Отменённые импортные
записи не активируются повторно.
