# Silence contract v1

Машинный формат: `contract-v1.schema.json`; сообщения и сценарии: `fixtures-v1.json`.

## 1. Источник состояния и время

- Правило хранится в БД Keep. `dismissed` в DTO — вычисляемый признак
  `effective.silenced`, а не enrichment, меняющий `status`.
- Исходные статусы, сохранение событий, история, корреляция, ack/resolve и
  ненотификационные действия workflow продолжают работать.
- Входные и выходные даты — UTC RFC 3339 с суффиксом `Z`; точность до микросекунд.
  Активный интервал — `[starts_at, ends_at)`. `ends_at=null` означает бессрочно.
- В create `starts_at=null` означает время первого принятия команды сервером.
  Повтор команды не вычисляет его заново. Явное начало в прошлом запрещено;
  импорт исторических правил — отдельная внутренняя операция миграции.
- Конечная дата должна быть позже начала и, для create/update, текущего времени.
  Срок в командах абсолютный: retry «продлить до 12:00» не превращается в ещё час.

| Состояние на `evaluated_at` | Условие |
| --- | --- |
| cancelled | `cancelled_at != null` |
| scheduled | отмены нет, время меньше `starts_at` |
| active | отмены нет, время не меньше начала и меньше конца, либо конца нет |
| expired | отмены нет, конечная дата наступила |

Решение об отправке всегда использует серверные часы и актуальную запись.
Задержка worker не продлевает silence. Отмена и истечение не переигрывают
накопленные уведомления и не запускают ремедиацию повторно. Отправка,
уже начавшаяся до успешной команды, не может быть отозвана: гарантия действует
на проверки перед последующими вызовами провайдера, включая каждую попытку retry.

## 2. Tenant, команды и права

Tenant устанавливает сервер из аутентификации. Один silence относится ровно
к одной команде; `team_id=null` относится **только к объектам без владельца**,
это не wildcard по tenant. Имена команд берутся из IaC без OPS/IT в коде.

| Оператор | Чтение | Создание / изменение / отмена |
| --- | --- | --- |
| admin | весь свой tenant | любая команда своего tenant, включая unassigned |
| responder | согласно политике видимости | только команды своего членства |
| viewer / noc | согласно политике видимости | запрещено |
| webhook / workflowrunner | нет нового права автоматически | запрещено |

Scopes: `read:silence`, `write:silence`, `update:silence`. Responder получает
последние два точечно в 16. READ_ONLY запрещает все пользовательские изменения.
`visibility: all` и `visible_to` не расширяют права записи. Интеграционный
сервис дополнительно ограничен своими разрешёнными командами и tenant.

Для записи сервер проверяет canonical owner из БД, всю историю fingerprint и
все цели selector. Чужая/смешанная/неподтверждённая история недоступна для
изменения responder. Admin может выбрать конкретную команду для такого
fingerprint: правило всё равно покрывает только события с этим owner.
Неизвестный ID не создаёт «будущую» цель; нужен существующий объект либо CEL.

Групповая команда атомарна: один недоступный объект означает отказ без нового
правила, audit и outbox. Даже admin создаёт отдельные правила для разных команд.
У правила нельзя изменить tenant/team. Если позднее связи или owner изменились,
пересчёт не расширяет правило на чужую команду. CEL, origin и correlation не
дают прав и не заменяют обязательную проверку owner.

Список, прямой ID, effective, счётчики и lifecycle-доставка применяют одну
политику видимости. Чужой скрытый объект — 404 без ID/названия в ошибке;
видимый объект без права записи — 403. Payload события разрешён только
подписчику соответствующего tenant/team.

## 3. Selector и покрытие

В v1 есть ровно три формы selector, без смешения между ними:

| `kind` | Поле | Поведение |
| --- | --- | --- |
| alert | `fingerprints` | все повторные события перечисленных fingerprint в выбранной команде |
| incident | `incident_ids` | перечисленные инциденты и их текущие связанные алерты той же команды |
| filter | `cel` | фильтр по данным алерта выбранной команды, включая будущие события |

Для CEL использовать имеющийся `celpy` и нормализацию severity из
`preprocess_cel_expression`. Переменные — поля canonical `AlertDto` на верхнем
уровне, как в alert workflow; например `service == 'database'`. Нет отдельного
incident CEL, запросов в сеть, enrichment-записей и полномочий через выражение.
Поля `dismissed` и silence metadata исключены из activation, чтобы не создавать
самозависимость. Синтаксис проверяется до записи; при вычислении ошибка поля
или результат не bool означает «не совпало» с диагностикой. CEL с
`status == 'firing'` не покрывает resolved — для обоих статусов нужен подходящий
фильтр или selector fingerprint/incident.

Для effective по fingerprint используется последний сохранённый алерт.
Перед реальной отправкой проверяется canonical событие, которое отправляется,
а не присланные клиентом status/team/metadata. Данные из очереди сами по себе
не подтверждают owner. Период правила проверяется в момент отправки, независимо
от времени исходного события.

### Алерт

Алерт silenced, если есть хотя бы одно активное правило его tenant/team:
прямой fingerprint, совпавший CEL либо явный selector связанного инцидента.
Ack, resolve и новое событие не отменяют правило. Изменение данных может
изменить совпадение CEL; это не изменение самого правила.

### Инцидент

1. Активный явный selector этого инцидента подавляет его целиком, включая
   инцидент без алертов, и распространяется на новые связи той же команды.
2. Иначе набор для покрытия — последние связанные алерты со статусами
   `firing`/`acknowledged`. Для отправки resolved-инцидента проверяются все
   последние связанные неудалённые алерты, включая resolved, чтобы завершение
   не обходило silence. Исторические версии не увеличивают этот набор.
3. Непустой набор полностью покрыт — `coverage=full`, `silenced=true`.
   Часть покрыта — `coverage=partial`, `silenced=false`: отправляются только
   непокрытые объекты. Ни один / пустой набор — `coverage=none`, `silenced=false`.
4. Partial payload строится заново из допустимых алертов. Текст, вложения,
   summary и агрегаты, содержащие подавленные данные, нельзя отправить из
   исходного общего шаблона. Если безопасно отделить данные невозможно,
   notification-шаг пропускается с диагностикой; остальной workflow продолжается.

Один алерт может принадлежать двум инцидентам. Явное правило первого покрывает
отправку этого алерта и может дать full/partial второму. **Вычисленный full
второго не распространяется обратно на его алерты или другие инциденты**:
учитываются только прямые правила и явные incident selectors, без рекурсии.
Merge/split не переносят ID selector на новый инцидент; пересчитываются связи
существующих целей. Для нового ID требуется новое правило/явное изменение. Для IaC lifecycle
закрытый эпизод не распространяет ID selector через fingerprint на более позднее
событие нового эпизода. Старый ID и его resolved notification остаются покрытыми;
reopening того же ID сохраняет правило. См. `../incident-core/lifecycle.md`.

### Несколько правил и срок в effective

- Все совпавшие правила возвращаются с ID/revision и причиной применения.
  `Unsilence` отменяет выбранные ID, а не все правила fingerprint.
- `silenced_until=null` при `silenced=false` или бессрочном покрытии; флаг
  различает эти случаи. Это граница **текущего покрытия**, не обещание будущего.
- Для алерта берётся самый поздний конец совпавших правил; бессрочное сильнее.
  Для покрытия всех алертов инцидента — самый ранний из таких концов; явное
  правило инцидента может продлить её. Будущие scheduled-правила и будущие
  изменения данных/связей сюда не включаются; receiver делает новый effective.
- Ответ содержит `evaluated_at`, `coverage`, причины и количества покрытых
  алертов. Incident effective считается по всему набору в БД, без лимита страницы
  500; клиент не повторяет CEL и не вычисляет покрытие по обрезанному списку.

Групповой MM-пост — явный snapshot `incident_ids` одной команды. Новый участник
поста не наследует список целей. Сайленс может стать partial; расширение требует
новой авторизованной команды. `post_id` не является selector или разрешением.

## 4. HTTP API и ресурс

Префикс остаётся `/silences`, как у routes этого форка; версия 1 содержится
в каждом документе `schema_version`. Не добавлять обязательных полей к старому
`/notify` моста. Breaking change получает новую версию контракта.

| Метод / путь | Запрос | Успех |
| --- | --- | --- |
| POST `/silences` | `CreateCommand` | 201 `MutationResponse`, Location с ID |
| GET `/silences/{id}` | — | 200 `Silence` |
| GET `/silences` | `state`, `team_id`, `limit`, `cursor` | 200 `SilenceList` |
| PATCH `/silences/{id}` | `UpdateCommand` | 200 `MutationResponse` |
| POST `/silences/{id}/cancel` | `CancelCommand` | 200 `MutationResponse` |
| POST `/silences/effective` | `EffectiveQuery` | 200 `EffectiveResponse` |

Список: `limit` по умолчанию 50, максимум 200, порядок `(created_at DESC, id DESC)`;
opaque cursor связан с фильтрами и авторизованной областью. Список targets
и списки selector ограничены 1000 уникальными элементами; превышение — 422.
Effective-запрос читает единый snapshot и либо возвращает все цели в порядке
запроса, либо общий отказ, без частичной утечки данных.

Входные команды не принимают `tenant_id`, actor, role, groups, origin, revision
или неизвестные поля. `team_id`, selector и correlation проходят проверки,
`created_by`/`updated_by`/origin устанавливает сервер. У actor есть стабильный
subject и тип `user`/`service`; email/display name не являются идентификатором
полномочий. UI вход через существующий доверенный OAUTH2PROXY; интеграционная
проверка стабильного OIDC subject описана ниже.

Ресурс содержит ID, revision, tenant/team, selector, период, comment, создателя
и последнего оператора, created/updated/cancelled_at, origin/correlation,
вычисленные state/evaluated_at. Origin ресурса — источник создания;
origin lifecycle-события — источник конкретного изменения.
Получатели игнорируют незнакомые поля ответа, но не неизвестную schema_version.

`tenant_id` — строковый ID Keep, а не обязательный UUID: в этой OSS-конфигурации
`SINGLE_TENANT_UUID` равен `keep`. UUID используются для silence/incident/event
и `client_request_id`.

Для списка отсутствие `team_id` означает все доступные команды, `team_id=` —
только unassigned; непустое значение выбирает конкретную команду.

PATCH разрешён только для scheduled/active. Update принимает `changes`:
selector, starts_at, ends_at, comment; минимум одно
поле. Selector проверяется заново атомарно. Начало active-правила неизменно;
scheduled можно перепланировать до его начала. Продление — обычный PATCH с
абсолютным ends_at. Expired/cancelled нельзя оживить: создаётся новое правило.
Cancel сохраняет запись, причину и оператора. Повторная отмена уже cancelled
с новой командой возвращает текущее состояние без нового события; revision
всё равно проверяется. Отмена expired — 409.

### Idempotence и concurrency

- `client_request_id` обязателен для каждой команды и уникален в tenant для
  аутентифицированного клиента/оператора. Сохраняется вместе с command hash,
  результатом и изменением правила в одной транзакции.
- Ключ не переиспользуется после рестарта/отмены. Receipt хранится не меньше
  самой записи и audit, без автоматического TTL в v1.
- Идентичный повтор возвращает тот же `result` и исходный HTTP status,
  `replayed=true`. В `result` исходный snapshot, не текущий срок; актуальное
  состояние получают GET/effective. Аутентификация и доступ проверяются снова.
  Receipt проверяется до повторной валидации периода/state/revision: уже
  принятая команда не становится ошибкой из-за истечения срока между retries.
- Hash включает метод, ID ресурса и нормализованное тело; порядок JSON-полей
  не важен, списки selector трактуются как множества. Тот же ключ с другим
  содержимым — 409 `idempotency_conflict`, до проверки expected_revision.
- PATCH/cancel требуют `expected_revision`. После неуспешного запроса receipt
  не фиксируется. Устаревшая ревизия — 409 `revision_conflict`, с текущей
  ревизией только для доступного ресурса. Клиент перечитывает и подтверждает
  новую правку; сервер не повторяет конфликтующий update автоматически.
- Любое зафиксированное изменение/переход lifecycle увеличивает revision
  ровно на 1. Проверка/чтение/effective её не меняют. Accepted no-op правка
  возвращает текущую ревизию без события. Серверный переход времени также
  может привести к revision_conflict.

Ошибки сохраняют форму FastAPI `detail`, но с объектом `code`, `message`,
`field`, `current_revision` (последние два могут быть null). 401 — нет/невалидна
identity; 403 — нет права; 404 — не найдено/скрыто; 409 — конфликт;
422 — shape/time/CEL/разные команды; 503 — невозможно проверить identity или
прочитать правила. При сбое проверки notification не отправляется, остальные
действия не запрещаются; этот случай записывается как ошибка проверки, а не silence.

## 5. Проверка будущей delegated-команды

Источник групп/ролей — **подписанные claims реального пользователя в IdP**,
которые проходят ту же IaC `TeamPolicy`, что обычный вход. В проверенной лабе
источник — Keycloak за OAUTH2PROXY. IdP/issuer, audience, JWKS URL,
group claim и разрешённые integration clients задаются IaC.

Пути команд интеграции — POST `/integrations/silences`, PATCH
`/integrations/silences/{id}`, POST `/integrations/silences/{id}/cancel`.
JSON и сервис БД те же, что у `/silences`; dependency аутентификации отдельная,
не использует legacy impersonation. GET list/get и POST effective под этим же
префиксом доступны сервису только в его IaC-области чтения. Integration client
не получает право писать через обычный `/silences` без proof.

Для delegated create/update/cancel Keep требует одновременно:

1. Ограниченную сервисную identity (`X-API-KEY`) integration client.
2. Короткоживущий **пользовательский OIDC access token** в
   `X-Keep-Actor-Token`: подпись разрешённым алгоритмом, pinned issuer/JWKS,
   правильный audience, exp/nbf/iat, стабильный sub, полные пути group claim.
   `alg=none`, ID token, client-credentials/service subject и неизвестный
   issuer/audience не подходят. Token не старше 5 минут; refresh требует
   нового пользовательского подтверждения/аутентифицированного сеанса.
   IaC задаёт разрешённые интерактивные `azp/client_id` и профиль issuer,
   позволяющий отличить user access token от service/ID token. Если issuer
   такого подтверждения не даёт, delegated-запись не включается.
3. Пересечение разрешённых tenant/team сервиса с настоящими scope/team
   оператора. JWT role string не принимается как готовая роль Keep:
   вычисление только из групп по конфигурации. READ_ONLY действует и здесь.

Actor proof — только заголовок, никогда body, MM context, лог или lifecycle.
`X-KEEP-USER`, `X-KEEP-ROLE`, email, user_id callback и состав канала его не
заменяют. При отсутствующем/невалидном proof — 401 `actor_proof_required` /
`invalid_actor_proof`; при невозможности проверки — 503, без admin fallback.
Обычный admin API key без actor proof не проходит delegated-путь.
Обычные `/silences` тоже отклоняют legacy `X-KEEP-USER`/`X-KEEP-ROLE`
impersonation: admin API записывает действие как service, не как чужого человека.

**Сейчас мост не располагает таким proof.** В будущем для кнопки нужен вход
оператора через доверенный OIDC/Keep-сеанс и подтверждение конкретной команды;
если токен нельзя безопасно получить, кнопка даёт ссылку на подтверждение в
Keep, а не делает запись от сервисного admin. Учётная запись MM может служить
контекстом; в audit оператором является проверенный sub. Проверка происхождения
MM callback остаётся обязанностью переделки моста и не повышает права Keep.
Транспорт и access к secrets настраиваются при 20/21; здесь они не включены.

## 6. Dispatch и lifecycle

Маркер ACTION в YAML: **`notification: true`** для исходящей отправки;
`notification: false` для остальных действий. В режиме новых сайленсов
классификация ACTION обязательна: непомеченные workflow должны попасть в
inventory/перенос до включения, а не тихо обходить gate. `provider.notify()`
сам по себе не классификатор. HTTP actions двух bridge workflow помечаются
как отправка в примерах fork; исходные bridge YAML здесь не меняются.

Gate стоит перед вызовом провайдера и каждой попыткой retry, после перечитывания
правил и перед безопасным рендерингом пакета. Это относится к очереди, manual,
scheduled и foreach. Если весь набор подавлен, шаг skipped: `results=null`,
`skipped=true`, `skip_reason="silenced"`, ID причин в execution metadata.
Не имитировать успешный provider response. Независимые actions продолжаются;
action, требующий отсутствующий результат silenced-шага, помечается skipped
с `skip_reason="missing_step_result"`, без выдуманных значений. Это требование
к реализации 17: нынешнее рендерирование aliases само по себе такого пропуска
не гарантирует.

Служебные `silence.created/updated/activated/cancelled/expired` не проходят
обычный notification gate. Событие и новая запись/revision/outbox фиксируются
атомарно. Доставка может опоздать, повториться или прийти не по порядку;
проблема receiver не откатывает правило.

- Событие содержит event_id, schema_version, event_type, occurred_at,
  effective_at, silence_id/revision, tenant/team, origin/correlation,
  client_request_id (null для часов), actor и полный ресурс на этот момент.
- occurred_at — время фиксации события; effective_at — начало действия
  изменения. Для часов это точные starts_at/ends_at, даже при задержке worker.
- Worker под блокировкой проверяет актуальные даты/отмену/revision.
  Устаревший timer не публикует activated/expired для уже изменённого периода.
  Если пропущено всё окно, публикуется только expired с текущим snapshot,
  без исторической activation и без воспроизведения уведомлений.
- Cancel/update и timer сериализуются; проигравшая команда с прежней ревизией
  получает 409, проигравший timer перечитывает запись. Failed команды не
  публикуют событий. Timer actor — сервис Keep, origin `keep-system`.
- Повтор доставки сохраняет event_id и payload. Получатель хранит последнюю
  revision на ID, игнорирует старые/повторные и при разрыве перечитывает GET
  и effective. Даже новый доставленный snapshot может устареть по времени:
  перед отправкой всегда новый effective, не сохранённый event.state.
- Ответ GET/effective корректен и до того, как worker зафиксировал переход.
  Ревизия snapshot может ещё не отражать такое изменение часов; это допустимо.
- MM-origin событие доставляется обратно как подтверждение/проекция, но
  receiver не превращает его в create/update-команду. Correlation помогает
  связать сообщения, не является дедупликацией вместо event_id/revision.

## 7. Проверка

Схема проверяет форму, типы, обязательные поля и запрет actor в командах.
Периоды, права, совпадение CEL, idempotence и покрытие проверяются с БД.
Сценарии `fixtures-v1.json` задают ожидаемые результаты. Валидатор проверяет
примеры, отрицательные формы и согласованность ID/revision/time между сообщениями.
Миграция исторических Maintenance/Dismiss описана в `migration.md`.
